# Remote-SSH engine commands

Remote-SSH (Mode B in [the server edition design](server-edition/architecture.md))
lets the desktop app use an engine on a server through the user's own SSH
account, like VS Code Remote-SSH. The engine listens only on `127.0.0.1` and the
desktop reaches it through `ssh -L`. Nothing new is exposed on the network.

These commands are what the desktop app runs over SSH. They also work by hand.

```sh
mira remote attach --json   # start or reuse this user's engine, print port + token
mira remote status --json   # is an engine running for this MIRA_HOME?
mira remote stop            # stop a standalone or Remote-SSH engine
mira remote setup           # point ~/.mira/bin/mira at this install (see below)
```

## Contract (protocol 1)

The desktop app runs:

```sh
ssh <host> -- sh -lc 'mira remote attach --json'
```

With `--json`, stdout carries exactly **one line of JSON** and nothing else. All
logs go to stderr.

Success (exit code 0):

```json
{"protocol": 1, "ok": true, "port": 18790, "token": "<gateway token>",
 "version": "0.4.0", "pid": 12345, "mira_home": "/home/alice/.mira", "started": true}
```

- `started` is `true` when this call started the engine and `false` when it reused a running one.
- `port` is the engine's port on the server's `127.0.0.1`. The desktop forwards it with
  `ssh -N -L <local>:127.0.0.1:<port> <host>`.
- `token` is the gateway token ([gateway auth](gateway-auth.md)). Keep it in memory only.

Failure (exit code 1):

```json
{"protocol": 1, "ok": false, "error": {"code": "start_failed", "message": "..."}}
```

| `code` | Meaning |
| --- | --- |
| `start_failed` | The engine exited during startup (message carries the last log line), or the port was answered by another process. |
| `health_timeout` | The engine did not answer `/health` in time (`--timeout`, default 30 s). It may still be starting; retry. |
| `lease_conflict` | The engine for this `MIRA_HOME` runs on another host sharing the home directory, or (for `stop`) it is managed by a system service. |
| `listener_mismatch` | The engine's port is answered by a process other than the engine holding the lease (for example another account squatting the port). The token is not sent; retry, or stop the other process. |
| `config_invalid` | The Mira config cannot be loaded, the running engine rejects the local token, or it listens on an address an SSH tunnel to `127.0.0.1` cannot reach. |
| `launcher_conflict` | (`setup`) A file not generated by Mira is at `<MIRA_HOME>/bin/mira`. |
| `unsupported`, `unsupported_platform` | (`setup`) A bundled engine, or Windows. |
| `internal` | Anything unexpected. |

`mira remote status --json` returns `{"protocol": 1, "ok": true, "running": false, "mira_home": ...}`
or the success shape above plus `"running": true` and `"hostname"`. The token is
included only when the engine runs on this host. `mira remote stop --json`
returns `{"protocol": 1, "ok": true, "message": ...}` and exits 0 when the engine
stopped or was not running.

## Behaviour

- **One engine per `MIRA_HOME`.** Attach uses the single-engine lease
  ([service lifecycle](service-lifecycle.md)). It reuses a healthy engine whatever
  started it (system service, `mira gateway`, an earlier attach), as long as it
  listens on loopback or all interfaces.
- **Starting.** Attach runs `mira gateway --host 127.0.0.1` on port 18790, or on a
  random free port when 18790 is taken, and waits for `/health`. An engine started
  this way refuses any non-loopback bind. If another process takes the port between
  the check and the bind, the gateway exits with code 4 (see below) and attach picks
  another port. Attach never stops a process to free a port.
- **Detached.** The engine runs in its own session (`setsid`; on Windows a detached
  process group), so closing SSH or letting the laptop sleep does not stop it. Its
  output goes to `<MIRA_HOME>/logs/remote-gateway.log`.
- **Stopping.** `mira remote stop` sends SIGTERM to a standalone or Remote-SSH
  engine after checking its PID belongs to a Mira gateway, and waits up to 15 s.
  Service-managed engines are left to `mira-engine stop`.

### Gateway shutdown and exit codes

`mira gateway` (and the bundled `mira-engine run-gateway`) handles SIGTERM and
SIGINT (Ctrl+C; also Ctrl+Break on Windows):

1. It stops accepting connections and closes open WebSockets with code **1001**
   (going away).
2. It stops the channels, cron and heartbeat, and closes MCP servers.
3. It releases the engine lease (removes `<MIRA_HOME>/engine.lease`) and exits
   with code **0**.

Shutdown is bounded at 10 s. If it takes longer, the engine releases its lease and
exits with code **1**. A second signal skips the wait: the engine releases its lease
and exits at once with code 128 + signal number (130 for SIGINT, 143 for SIGTERM).
`kill -9` still leaves a lease record behind; it is recognised as dead and replaced.

| Exit code | Meaning |
| --- | --- |
| `0` | Stopped cleanly after SIGTERM or SIGINT. |
| `1` | Startup error, or shutdown hit the 10 s limit. |
| `3` | Another engine already holds the lease for this `MIRA_HOME`. |
| `4` | The port is held by a process the gateway must not stop (see below). |
| `128 + n` | A second signal `n` forced the exit. |

### Port already in use

Before binding, the gateway checks the port. It stops the holder only when it can
prove the holder is a leftover Mira engine for the **same** `MIRA_HOME`: owned by the
same user, running a Mira gateway command, tied to this `MIRA_HOME` by its environment
or the local gateway registry, and not the engine that holds the lease. That engine
gets SIGTERM and up to 15 s to exit.

Anything else is left alone, including processes of other users and Mira engines
for another `MIRA_HOME`. The gateway then exits with code 4 and names the holder:

```text
Error: port 18790 on 127.0.0.1 is already in use by pid 4242 (python3: python -m http.server 18790), which is not a Mira engine.
Mira only stops a leftover engine for this MIRA_HOME. Stop that process, or start the gateway on another port with --port.
```

## Finding `mira` over non-interactive SSH

`ssh host -- sh -lc '...'` starts a login shell, which reads `~/.profile` (and,
for bash, `~/.bash_profile` or `~/.bash_login`). It does **not** read `~/.bashrc`,
where conda and many venv setups put their PATH changes. So a pip install into a
conda env or venv is usually not on the PATH the desktop app sees.

### The launcher

Mira keeps a small POSIX `sh` launcher at `${MIRA_HOME:-$HOME/.mira}/bin/mira`
(mode 0755):

```sh
#!/bin/sh
# Generated by mira (mira remote setup). Do not edit; mira rewrites this file.
# mira-generated-launcher: 1
exec '/home/alice/miniconda3/envs/mira/bin/python' -m mira_engine "$@"
```

It calls the env's interpreter directly, so it works without activating the env.

- **Automatic.** Every `mira` command from a pip install checks the launcher.
  It writes one when none exists, or when the existing generated launcher points
  at an interpreter that no longer exists. A valid launcher for another install is
  left alone. This check is silent and never fails the command.
- **Explicit.** `mira remote setup` always points the launcher at the current
  install. Run it once after `pip install`, or after switching to another env:

  ```sh
  conda activate mira && mira remote setup
  ```

  `mira remote setup --json` prints
  `{"protocol": 1, "ok": true, "launcher": "/home/alice/.mira/bin/mira", "executable": "...", "version": "..."}`.
- **Your own file wins.** Mira only rewrites a launcher that carries the
  `# mira-generated-launcher:` marker. If something else is at that path, `setup`
  fails with `launcher_conflict` and leaves it untouched.
- **Opt out** with `MIRA_NO_LAUNCHER=1`. The launcher is never written by bundled
  (PyInstaller) engines or on Windows; there `setup` fails with `unsupported` or
  `unsupported_platform`.

### How the desktop app finds the engine

For each host, the desktop app tries, in order:

1. The manual path set for that host, if any. When set, it is the only one tried.
2. `${MIRA_HOME:-$HOME/.mira}/bin/mira`.
3. The last path that worked for that host.
4. `command -v mira` in `sh -lc`.

If none works, the app offers to install the engine. With your consent it
creates `${MIRA_HOME:-$HOME/.mira}/venv` using `uv`, or Python 3.11 or newer,
installs `mira-engine` there without sudo, and runs `mira remote setup`.

### Manual fallback

Check what the app will see with:

```sh
ssh <host> -- sh -lc '${MIRA_HOME:-$HOME/.mira}/bin/mira --version || command -v mira'
```

If you cannot use the launcher, set the per-host path in the desktop app, or put
`mira` on the login shell's PATH: install with `pipx install mira-engine` (or
`uv tool install mira-engine`), symlink the env's entry point into `~/.local/bin`,
or add its directory to PATH in `~/.profile` rather than `~/.bashrc`.

## Servers with systemd-logind

`/run/user/<uid>` (the default runtime dir) is removed when the user's last
login session ends. On some distributions, logind also kills the user's processes
then (`KillUserProcesses=yes`). Either can surprise a long-running engine. To
avoid both, run:

```sh
loginctl enable-linger $USER
```

Alternatively, set `MIRA_RUNTIME_DIR` to a persistent local directory.
